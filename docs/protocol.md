# Проектирование протокола

Реализованы защищённый канал, подписанные приглашения и кадры сообщений версии 1.
Живые диалоги реализованы в `chat`; постоянное хранение, повторная доставка
и сетевой запрос знакомства ещё не реализованы.

Транспорт версии 1: onion v3, TCP через SOCKS5 Tor, виртуальный порт `443`.
Порт обозначает поток ShadowTalk, а не HTTPS. Узел публикует адрес, устойчиво
выведенный из отдельного ключа профиля; имя не проходит через DNS.
Поверх потока применяется описанный ниже защищённый канал. Детали запуска —
в [ADR 0006](decisions/0006-managed-tor-transport.md).

## Защищённый канал версии 1

- TLS 1.3, обязательный ALPN `shadowtalk/secure/1`, без возобновления сессий.
- Каждая сторона предъявляет один самоподписанный Ed25519-сертификат и доказывает
  владение приватным ключом в TLS. Ключ должен точно совпасть с заранее заданным
  публичным ключом собеседника; доверие по DNS, центру сертификации или нику не используется.
- После успешной проверки клиента сервер пишет байт `0x01` внутри TLS-потока.
  Клиент считывает и проверяет его до возврата готового канала. Это подтверждение
  установки соединения, а не подтверждение доставки пользовательского сообщения.
- Дальнейшие байты принадлежат протоколу приложения. Канал не задаёт границ сообщений.

Требования к сертификату, отмене и ресурсам описаны в
[ADR 0005](decisions/0005-pinned-tls-channel.md). Первое получение доверенного ключа
и допуск нового контакта не входят в этот модуль.

Менеджер `peers` принимает входящие потоки по набору сохранённых ключей через
`ServerForPeers`, затем сопоставляет фактически проверенный ключ с контактом.
Набор фиксируется на время работы менеджера. Исходящее соединение проверяет один
конкретный ключ по локальному имени контакта. Дополнительных сетевых сообщений
менеджер не добавляет: ALPN и байт подтверждения версии 1 остаются прежними.
Повторные и встречные подключения остаются отдельными потоками. `chat` объединяет
их по проверенному ключу в один диалог, сохраняя не больше одного потока каждого
направления. Wire-формат при этом не меняется; правила описаны в
[ADR 0010](decisions/0010-chat-core.md).

## Кадры сообщений версии 1

Поверх готового `peers.Session` применяется `internal/protocol`. После TLS и
его байта подтверждения передаются кадры:

```text
4 байта: uint32 big-endian N | ровно N байт: UTF-8 JSON
```

Длина не включает заголовок. Допустимо `1 <= N <= 131072` (128 КиБ); проверка
выполняется до выделения памяти под тело. Неполный кадр — ошибка, даже если
соединение закрылось штатно. EOF без ошибки усечения возможен только перед
первым байтом следующего заголовка.

Два типа тела, поля строго в показанном порядке:

```json
{"version":1,"type":"text","id":"00112233445566778899aabbccddeeff","text":"Привет\nhello"}
{"version":1,"type":"ack","id":"00112233445566778899aabbccddeeff"}
```

Это два отдельных примера тел, каждый получает собственный заголовок длины.

| Поле | Правило |
| --- | --- |
| `version` | Целое число `1`, без дробной или экспоненциальной формы |
| `type` | Только `text` или `ack` |
| `id` | 32 hex-символа `[0-9a-f]`, ненулевой 128-битный ID |
| `text` | Только для `text`: непустой корректный UTF-8, максимум 16384 байта после декодирования |

Версия 1 использует каноническую сериализацию `encoding/json.Marshal` для этих
полей: нет BOM, пробелов вне строк, дополнительных значений, неизвестных или
повторных полей. Регистр имён значим; `text` у ACK отсутствует целиком, даже
пустая строка или `null` недопустимы. JSON не форматируется с отступами.

В строках кавычка и обратная косая черта записываются как `\"` и `\\`.
Backspace, form feed, LF, CR и tab — как `\b`, `\f`, `\n`, `\r`, `\t`.
Остальные символы U+0000–U+001F — `\u00xx` с нижним регистром hex.
`<`, `>`, `&`, U+2028 и U+2029 записываются соответственно как `\u003c`,
`\u003e`, `\u0026`, `\u2028`, `\u2029`. Остальной Unicode передаётся непосредственно
в UTF-8, `/` не экранируется. Альтернативные escapes, surrogate pairs в JSON
и непарные суррогаты отклоняются; emoji передаются в UTF-8. Нормализации текста нет.

ID создаётся один раз при создании сообщения и сохраняется для повторов.
ACK повторяет ID полученного текста. Он означает постоянное сохранение получателем,
не прочтение человеком. Кодек только читает и пишет ACK; право отправить его
возникает у будущего слоя доставки после успешного сохранения. Подтверждение
сопоставляется с исходящим сообщением именно этому проверенному собеседнику.

Полей отправителя и адресата нет: контакт определяется аутентифицированной сессией.
Время и порядок локальной истории принадлежат приложению. Защиту от дублей нужно
строить по паре «ключ отправителя + ID», а не по ID от всех собеседников вместе.

`Reader` и `Writer` используют один экземпляр на направление потока. Reader не
читает вперёд; Writer не допускает перемешивания конкурентных кадров. Ошибка чтения
или I/O записи окончательна, включая timeout: объект больше не обращается к потоку,
вызывающий код закрывает соединение. Ошибка проверки исходящего Frame не пишет
байтов и допускает исправление. Дедлайны и отмена задаются на самом соединении.
Отдельных error/hello/ping-кадров и согласования версий пока нет.
Подробности — [ADR 0009](decisions/0009-message-protocol.md).

## Приглашение v1 и первое доверие

Формат: `shadowtalk://invite/v1/` + unpadded base64url канонического UTF-8 JSON.
Лимит — 2048 байт всего токена. Поля envelope в точном порядке: `payload`,
`signature`. Поля payload: `version`, `nickname`, `onion`, `public_key`, `id`,
`issued_at`, `expires_at`. `version` равен 1; последние два поля — целые Unix-секунды.
Строки `public_key` и `id` кодируют по 32 байта тем же base64url; `signature` — 64 байта.
`id` — публичный случайный идентификатор, не секрет доступа.

Подпись Ed25519 вычисляется ключом профиля над байтами
`ShadowTalk/invitation/v1\x00` (последний байт — NUL), затем компактным JSON payload.
JSON не содержит пробелов между полями. Ники и адреса ограничены ASCII, остальные
строки — base64url. При чтении повторное кодирование должно совпасть побайтно;
дубликаты, неизвестные поля, альтернативный порядок и неканонический base64 отклоняются.
Ник следует правилам профиля; onion v3 проверяется вместе с checksum.

Срок — от 1 секунды до 7 дней, по умолчанию 24 часа. На границе `now >= expires_at`
токен недействителен. `issued_at` может опережать локальные часы максимум на 5 минут.
При импорте проверка проводится заново, затем требуется точное совпадение полного
ожидаемого отпечатка `SHA256:` публичного ключа. Подпись удостоверяет данные владельца
ключа, но не имя человека: ключ сверяется по доверенному каналу.

В версии 1 оба участника обмениваются токенами и сохраняют контакты локально.
Так обе стороны знают ожидаемый ключ до вызова `securechannel`. Переданный токен
не расходуется, работает повторно до истечения срока и не отзывается выпуском нового.
Сохранённый контакт не истекает; удаление записи действует только на этом устройстве.
Входящий запрос по одному приглашению, одноразовое принятие и отзыв потребуют
отдельного протокола и постоянного состояния издателя. Сейчас они не реализованы.
Решение и отличие от раннего предложения — [ADR 0007](decisions/0007-signed-contact-invitations.md).

## Доставка

Формат ID и ACK определён выше. Постоянное сохранение, устранение дублей,
сопоставление подтверждений и повторы ещё не реализованы. Будущая очередь исходящих
сообщений должна переживать перезапуск, отправлять ACK только после фиксации записи
и повторно подтверждать уже сохранённые сообщения без добавления дубля в историю.
При отсутствии посредника доставка требует одновременного присутствия обоих узлов.

Текущее ядро чата только записывает текст и выдаёт события приёма. Полученный ACK
становится событием с ключом контакта и ID, без изменения статуса доставки.
Автоматических ACK и повторной отправки в `chat` нет. Успех Send подтверждает
запись кадра в поток, а не его сохранение получателем.
