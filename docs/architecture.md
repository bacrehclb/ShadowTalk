# Архитектура ShadowTalk

Реализованы метаданные профиля и операции с ключами в `identity`, сценарии
профиля и загрузка идентичности в `app`, адаптеры `storage/profilefile`,
`storage/keyring` и `storage/seedfile`, CLI в `cmd/shadowtalk`.
CLI и TUI связывают метаданные, шифрование и хранилище ОС в готовый сценарий профиля.
Отдельно реализован модуль `securechannel`; подключение его к приложению и Tor
остаётся следующим этапом. Остальные компоненты представлены каталогами.

## Границы компонентов

| Каталог | Ответственность |
| --- | --- |
| `cmd/shadowtalk` | Запуск ядра и интерфейса, обработка завершения процесса |
| `internal/app` | Сборка компонентов ядра и управление их жизненным циклом |
| `internal/identity` | Локальная идентичность, профиль и операции с ключами |
| `internal/contacts` | Приглашения, подтверждение контактов и блокировки |
| `internal/chat` | Диалоги, сообщения и правила общения |
| `internal/delivery` | Устойчивая очередь, подтверждения и устранение дублей |
| `internal/protocol` | Сетевые сообщения, кодирование, версии и ограничения |
| `internal/transport/tor` | Управление Tor и создание соединений |
| `internal/securechannel` | Защищённое соединение и проверка ключа собеседника |
| `internal/storage/profilefile` | Создание и загрузка метаданных профиля в JSON |
| `internal/storage/keyring` | Запись и чтение ключа шифрования seed в хранилище ОС |
| `internal/storage/profiledir` | Блокировка профиля, журнал создания и согласование файлов |
| `internal/storage/seedfile` | Создание и загрузка файла зашифрованного seed |
| `internal/storage/sqlite` | Локальное хранение, запросы и миграции |
| `internal/tui` | Терминальные экраны и обработка действий пользователя |

## Правила зависимостей

- Точка запуска связывает ядро и интерфейс. `app` не импортирует `tui`.
- Интерфейс вызывает операции ядра и отображает события; SQL и работа
  с сокетами в нём отсутствуют.
- Правила общения не зависят от Bubble Tea, SQLite или реализации Tor.
- Адаптеры хранения и соединений реализуют небольшие интерфейсы, определённые
  там, где они используются. Интерфейсы добавляются по реальной необходимости.
- Сетевые представления данных отделены от состояния экранов и схемы БД.
- Циклические импорты и глобальное изменяемое состояние не допускаются.

CLI связывает `app.Profiles` с `profiledir.Store` и `keyring.Store`.
Интерфейсы `ProfileFiles` и `EncryptionKeys` принадлежат `app`. `profiledir`
использует `profilefile` и `seedfile`, отвечает за формат журнала и повторяемую
публикацию файлов. `app` управляет порядком операций и проверяет соответствие
восстановленного публичного ключа профилю. `identity` не зависит от CLI,
файловой системы или формата JSON. TUI вызывает те же сценарии через адаптер
`profileUI` в точке запуска. Адаптер возвращает только `identity.Profile`:
приватные ключи не попадают в модель экранов и сообщения Bubble Tea.

`internal/tui/profile.go` отвечает за состояния и действия, `view.go` — за
раскладку и оформление, `run.go` — за проверку терминала и цикл Bubble Tea.
Операции приложения выполняются асинхронно, по одной за раз. UI получает их
результат отдельным сообщением; повторное нажатие не запускает вторую запись.
Правила ника остаются в `identity`, файловые операции и работа с ключами — в `app`
и адаптерах хранения. Подробнее — [ADR 0004](decisions/0004-profile-tui.md).

`Profiles` предоставляет `Create`, `Load`, `Upgrade` и `Recover`. `Load` ничего
не записывает и не создаёт идентичность для старых профилей. Остальные операции
держат межпроцессную блокировку через `gofrs/flock`; повторное восстановление
использует исходный журнал и ключ. После ошибки публикации ключ сохраняется
для восстановления, а не удаляется из-под уже записанного seed.
Порядок шагов и ограничения описаны в [ADR 0003](decisions/0003-profile-identity-lifecycle.md).

`keyring.Store` предоставляет `Set(id, key)`, `Get(id)` и `Delete(id)`. Это адаптер хранения,
а не сценарий создания идентичности. Он принимает отдельный 32-байтовый ключ;
стабильный несекретный ID задаёт вызывающий код, ник для этого не используется.
`Set` заменяет запись с тем же ID и проверяет результат чтением. Запись и чтение
не являются транзакцией; согласование записей и запрет замены используемого ключа
обеспечиваются сценарием `Profiles`: для новой идентичности выделяется случайный
256-битный ID и перед записью проверяется отсутствие такой записи.

`Delete` удаляет одну запись по ID; отсутствие записи считается успехом.
После успешного ответа об удалении адаптер проверяет отсутствие записи.
Если запись осталась или проверка недоступна, возвращается `ErrDeleteUnconfirmed`;
при ошибке доступа также распознаётся `ErrUnavailable`. Повторная проверка не
является транзакцией с удалением. Метод используется для очистки нового ключа
после ошибки его записи, до публикации файлов идентичности; выбор ID и согласование
операций остаются ответственностью вызывающего кода.

`seedfile.Store` предоставляет `Create(keyID, encryptedSeed)` и `Load()`.
Он принимает готовый шифротекст, возвращает ID ключа и шифротекст, не обращается
к хранилищу ОС и не выполняет расшифровку. Правила ID ключа общие для обоих
адаптеров и принадлежат `identity`. Формат JSON остаётся внутри `seedfile`.

`app.IdentityLoader.Load()` читает сохранённый seed, получает ключ по его ID,
расшифровывает seed и возвращает `identity.KeyPair`. Он зависит только от
`identity` и двух интерфейсов чтения, определённых в `app`: `EncryptedSeedReader`
и `EncryptionKeyReader`. Адаптеры связываются с загрузчиком вызывающим кодом.
Ошибки сохраняют причины для `errors.Is`; при ошибке возвращается пустая пара.
Загрузчик не создаёт, не исправляет и не перезаписывает данные.

## Защищённое соединение

`identity.KeyPair.Signer()` выдаёт `crypto.Signer`, который подписывает данные
существующим ключом без экспорта seed. Нулевую или несогласованную пару он отклоняет.
`securechannel.New` принимает идентичность и ограничение времени подключения;
созданный `Endpoint` можно использовать для нескольких соединений одновременно.

`Endpoint.Client` и `Endpoint.Server` получают `context.Context`, открытый
`net.Conn` и ожидаемый Ed25519-ключ другой стороны. Транспорт принадлежит модулю
с момента вызова, включая ошибки. После проверки TLS и подтверждения сервера
возвращается `securechannel.Conn`: интерфейс `net.Conn` и `PeerPublicKey()`.
Исходное соединение наружу не выдаётся. Контекст ограничивает только установку
канала; после успеха его время жизни и дедлайны чтения/записи задаёт вызывающий код.

`channel.go` управляет установкой соединения, `certificate.go` создаёт и проверяет
сертификаты, `conn.go` предоставляет поток данных. Сетевых адресов, Tor, хранилища
контактов и UI в модуле нет. Формат сообщений и повторная доставка относятся
к `protocol` и `delivery`. Первое доверие ключу должно быть установлено до вызова
канала. Подробности — [ADR 0005](decisions/0005-pinned-tls-channel.md).

## Технологии

Go, Bubble Tea для интерфейса и `crypto/tls` для защищённого канала.
Отдельный процесс Tor и локальная SQLite остаются в плане. Процедуру первого
знакомства выбираем вместе с реализацией приглашений и контактов.

Значимые решения записываем в `docs/decisions` отдельными файлами с номером,
контекстом, выбранным решением и последствиями.
