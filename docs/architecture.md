# Архитектура ShadowTalk

Реализованы метаданные профиля и операции с ключами в `identity`, сценарии
профиля в `app`, адаптеры `storage/profilefile`, `storage/keyring` и `storage/seedfile`, CLI
в `cmd/shadowtalk`. Хранение ключей пока не подключено к сценариям профиля.
Остальные компоненты представлены каталогами для дальнейшей реализации.

## Границы компонентов

| Каталог | Ответственность |
| --- | --- |
| `cmd/shadowtalk` | Запуск ядра и интерфейса, обработка завершения процесса |
| `internal/app` | Сборка компонентов ядра и управление их жизненным циклом |
| `internal/identity` | Локальная идентичность, профиль и операции с ключами |
| `internal/contacts` | Приглашения, подтверждение контактов и блокировки |
| `internal/chat` | Диалоги, сообщения и правила общения |
| `internal/delivery` | Устойчивая очередь, подтверждения и устранение дублей |
| `internal/protocol` | Сетевые сообщения, кодирование, версии и ограничения |
| `internal/transport/tor` | Управление Tor и создание соединений |
| `internal/securechannel` | Защищённое соединение и проверка ключа собеседника |
| `internal/storage/profilefile` | Создание и загрузка метаданных профиля в JSON |
| `internal/storage/keyring` | Запись и чтение ключа шифрования seed в хранилище ОС |
| `internal/storage/seedfile` | Создание и загрузка файла зашифрованного seed |
| `internal/storage/sqlite` | Локальное хранение, запросы и миграции |
| `internal/tui` | Терминальные экраны и обработка действий пользователя |

## Правила зависимостей

- Точка запуска связывает ядро и интерфейс. `app` не импортирует `tui`.
- Интерфейс вызывает операции ядра и отображает события; SQL и работа
  с сокетами в нём отсутствуют.
- Правила общения не зависят от Bubble Tea, SQLite или реализации Tor.
- Адаптеры хранения и соединений реализуют небольшие интерфейсы, определённые
  там, где они используются. Интерфейсы добавляются по реальной необходимости.
- Сетевые представления данных отделены от состояния экранов и схемы БД.
- Циклические импорты и глобальное изменяемое состояние не допускаются.

В текущем сценарии CLI связывает `app.Profiles` с `profilefile.Store`.
Интерфейс `ProfileStore` принадлежит `app`, который использует хранилище.
Пакет `identity` не зависит от CLI, файловой системы или формата JSON.
Терминальный интерфейс сможет использовать те же сценарии создания и загрузки.

`keyring.Store` предоставляет `Set(id, key)` и `Get(id)`. Это адаптер хранения,
а не сценарий создания идентичности. Он принимает отдельный 32-байтовый ключ;
стабильный несекретный ID задаёт вызывающий код, ник для этого не используется.
`Set` заменяет запись с тем же ID и проверяет результат чтением. Запись и чтение
не являются транзакцией; согласование записей и запрет замены используемого ключа
должны быть обеспечены при подключении адаптера к сценарию профиля.

`seedfile.Store` предоставляет `Create(keyID, encryptedSeed)` и `Load()`.
Он принимает готовый шифротекст, возвращает ID ключа и шифротекст, не обращается
к хранилищу ОС и не выполняет расшифровку. Правила ID ключа общие для обоих
адаптеров и принадлежат `identity`. Формат JSON остаётся внутри `seedfile`.

## Предлагаемые технологии

Go, Bubble Tea для интерфейса, отдельный процесс Tor, локальная SQLite.
Кандидат для защищённого канала — TLS 1.3 с проверкой закреплённых ключей.
Конкретные зависимости и процедуру знакомства выбираем перед реализацией.

Значимые решения записываем в `docs/decisions` отдельными файлами с номером,
контекстом, выбранным решением и последствиями.
