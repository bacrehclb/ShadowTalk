# 0003 Создание, загрузка и восстановление профиля

Статус: реализовано в CLI; формат резервного экспорта остаётся отдельной задачей.

## Форматы и команды

`profile.json` версии 2 добавляет `public_key`: 64 hex-символа публичного
Ed25519-ключа. Версия 1 остаётся читаемой; `profile upgrade` явно добавляет
идентичность, сохраняя ник и дату. `identity-seed.json` сохраняет формат версии 1.
Отпечаток `SHA256:<64 hex-символа>` вычисляется из 32 байт публичного ключа.
При загрузке приватная идентичность должна соответствовать публичному ключу
из метаданных. Готовый профиль с отсутствующим seed или ключом не пересоздаётся.

`profile create --nick NICK`, `profile show`, `profile upgrade`, `profile recover`
сохраняют общий `--profile-dir` перед подкомандой. Справка и чтение не создают
пользовательские файлы. Успешная операция возвращает 0, ошибка — 1, диагностика
идёт в stderr. `show` сначала завершает проверку, затем печатает весь результат.

## Координация

`app.Profiles` зависит от `ProfileFiles` и `EncryptionKeys`. Адаптер `profiledir`
координирует низкоуровневые `profilefile`, `seedfile` и журнал. Изменяющая операция
получает неблокирующий exclusive lock `.profile.lock` через
[`gofrs/flock`](https://github.com/gofrs/flock/tree/v0.13.2). Занятый профиль
возвращает ошибку сразу. Файл блокировки не удаляется: удаление может позволить
двум процессам захватить разные inode. После выхода процесса lock освобождается ОС.

Порядок создания или обновления:

1. Проверить существующие данные и отсутствие незавершённой операции.
2. Сгенерировать Ed25519-ключи, отдельный AES-256-ключ и случайный 256-битный ID.
   Проверить отсутствие ID в хранилище ОС.
3. Опубликовать `profile-pending.json`: версию журнала, тип операции, метаданные,
   публичный ключ, ID ключа и зашифрованный seed. Открытого seed и ключа в журнале нет.
4. Сохранить ключ в хранилище ОС и подтвердить запись чтением.
5. Опубликовать файл seed, затем метаданные профиля с публичным ключом.
6. Проверить соответствие обоих файлов журналу, удалить журнал и освободить lock.

Для новой записи используются временный файл, `Sync`, закрытие и `os.Link` без
перезаписи. Для явного обновления legacy-метаданных используется временный файл
и `os.Rename` под lock. Go не гарантирует атомарность `Rename` на всех платформах:
журнал сохраняется до проверки результата ([документация os.Rename](https://pkg.go.dev/os#Rename)).
Все три файла ограничены 4 КиБ. Координатор отклоняет symlink и специальные
файлы на местах метаданных, seed, журнала и lock. Сам каталог может быть доступен
через ссылку. Это предполагает доверенный пользовательский каталог, не защиту
от враждебных изменений владельцем этой же учётной записи.

## Частичные сбои

Ошибка записи ключа может возникнуть после фактического сохранения. До публикации
файлов можно удалить только свой новый ключ; если удаление подтверждено, журнал
отменяется. Если очистка не удалась, журнал остаётся для `profile recover`.

При ошибке публикации файлов ключ не удаляется. `recover` загружает именно ключ
и seed журнала, проверяет публичную идентичность и дописывает отсутствующие файлы.
Уже опубликованные файлы принимаются только при точном совпадении; конфликтующие
данные сохраняются и возвращают ошибку. Обновление legacy-профиля требует совпадения
исходных ника и даты. Чтение при наличии журнала предлагает `recover`.

Если ключ отсутствует и seed ещё не опубликован, можно отменить незавершённую
операцию без потери созданной идентичности: нового готового профиля ещё не было.
При опубликованных файлах отсутствие ключа является ошибкой восстановления;
автоматической смены идентичности нет. После аварийного завершения временные
файлы могут остаться; по ним не принимаются решения и они не содержат открытых секретов.

## Проверки и пределы

Тесты покрывают создание, повторное чтение, сохранность legacy-метаданных,
конкурентные процессы, аварийный выход после записи ключа и каждый этап публикации,
потерю ключа, несовпадение идентичности и ошибки доступа. Тестовый backend ключей
для дочерних процессов существует только в `_test.go`; в обычном бинарнике
нет настройки для хранения открытого ключа в файле.

На macOS отдельно проверены настоящий бинарник и Keychain с удалением тестового
ключа. Для Windows и Linux предусмотрен CI; реальные хранилища этих ОС пока
не проверены. Требуется файловая система с жёсткими ссылками и корректными
блокировками. Каталог отдельно не синхронизируется: это восстановление после
сбоя процесса, а не гарантия при потере питания. Перенос без ключа ОС не поддержан.
