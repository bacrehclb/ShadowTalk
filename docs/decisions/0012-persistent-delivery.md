# ADR 0012: постоянная очередь доставки и подтверждения

Статус: принято. Расширяет ADR 0010 и 0011; формат сетевых кадров и шифрование
текста истории не меняются.

## Контекст

Запись в сетевое соединение не доказывает сохранение сообщения собеседником.
Процесс может завершиться после отправки, а ACK — потеряться после фиксации
истории получателем. Нужен слой, который сохраняет исходящий текст до отправки,
повторяет его с прежним ID и подтверждает только записанный входящий текст.

## Решение

`internal/delivery` владеет очередью через интерфейс `Store` и сетью через `Network`.
Не импортирует SQLite, Tor или UI. `service.go` отвечает за API и завершение,
`receive.go` — за входящие сообщения/ACK, `retry.go` — за ограниченный планировщик.
`app.PeerSessions.StartDelivery` собирает профиль, контакты, хранилище, `peers`,
`chat` и `delivery` по одному снимку идентичности и контактов. Фабрика SQLite
передаётся вызывающим кодом; ключ очищается после вызова фабрики. Ошибка запуска
закрывает уже открытые компоненты. Успешный сервис владеет хранилищем и сетью.

### Исходящие сообщения

1. Вызывающий код один раз создаёт `chat.Message` через `chat.NewMessage(text)`.
   `Queue(ctx, peerPublicKey, message)` проверяет подтверждённого контакта,
   сохраняет историю и outbox **одной транзакцией**, затем будит планировщик.
2. Успех Queue означает постоянное локальное сохранение, не доставку. При
   неоднозначной ошибке повторяют тот же ID: одинаковый текст возвращает прежнюю
   запись, другой текст — `history.ErrConflict`. Доставленное сообщение повторный
   Queue не отправляет заново. Адресат — ключ, не изменяемое локальное имя.
3. `Due` выбирает только первое неподтверждённое сообщение каждого собеседника.
   Поздние сообщения этого диалога ждут его ACK. Между собеседниками выбор идёт
   по времени следующей попытки и sequence, без глобальной гарантии порядка.
4. Перед сетью `BeginAttempt` фиксирует число попыток и срок восстановления.
   Быстрый ACK может прийти до возврата Send и уже будет принят. Если процесс
   завершился до отправки или сразу после неё, запись снова станет доступной
   по истечении сохранённого срока. Вечного состояния «отправляется» нет.
5. Send использует существующий диалог или подключается через Tor/TLS. При любом
   результате исходящая запись остаётся `Pending`, пока не придёт корректный ACK.
   После отправки `Retry` назначает следующую попытку только всё ещё ожидающей
   записи с тем же счётчиком; параллельное подтверждение не перезаписывается.

### Входящие сообщения и ACK

Один обработчик читает аутентифицированные события `chat`. Текст сначала
записывается через `history.Append`, и только после успешной фиксации вызывается
явный `Dialog.Acknowledge`. Сам `chat` по-прежнему не решает, когда отправлять ACK.
Одинаковый входящий дубль не добавляется в историю, но подтверждается повторно.
Другой текст с тем же ключом отправителя и ID вызывает конфликт: исходная запись
сохраняется, ACK не отправляется, закрывается только диалог нарушителя.

Потеря соединения при ACK оставляет сообщение сохранённым. Для ACK новое
соединение не создаётся: отправитель повторит текст, и получатель повторит ACK.
Ошибка хранилища при приёме останавливает сервис и сеть без подтверждения.

Полученный ACK сопоставляется с **ключом проверенного собеседника и ID исходящей
очереди**. Непоставленные в очередь, ещё не пытавшиеся отправиться, неизвестные
и уже подтверждённые ID не меняют состояние. Запись с тем же ID другому контакту
или входящее сообщение не подходят. Успешная обработка фиксирует `Delivered`
и локальное `DeliveredAt`. Это заявление доверенного ключа о сохранении,
не доказательство честности удалённого приложения и не отметка прочтения.

### Ограничения и повторные попытки

| Настройка | По умолчанию |
| --- | --- |
| Одновременные отправки | 4, максимум 32, не больше одной на собеседника |
| Проверка очереди | Каждую секунду и по уведомлению Queue/ACK |
| Задержка повторов | 5 секунд, удвоение до 5 минут |
| Срок подключения и записи | 90 секунд на попытку |
| Ожидание ACK после успешной записи | Не меньше 30 секунд и задержки текущего повтора |
| Срок записи ACK | 5 секунд |
| Неподтверждённые исходящие | 10000 на профиль |

Предварительный срок восстановления — время начала + срок попытки + максимум
ожидания ACK и задержки повтора. После завершения попытки назначается обычная
задержка. Сроки сохраняются как абсолютные Unix milliseconds; большой перевод
системных часов может ускорить или задержать повторы. Задержка не содержит jitter.
Потерянные ACK могут вызывать повторную передачу, даже когда текст уже сохранён.

Неподтверждённые записи не удаляются по числу попыток. Если контакт удалён перед
следующим запуском, запись остаётся Pending; соединение с неизвестным ключом
не открывается. Изменения контактов применяются после перезапуска. Отмену очереди,
ручной сброс задержки и изменение контактов на лету добавит отдельный сценарий.
Лимит очереди не ограничивает общий размер уже сохранённой истории.

### Схема и миграция

SQLite получает `user_version=2` и таблицу `outbox` с внешним ключом на
`messages.sequence`, числом попыток, временем следующей попытки и nullable
`delivered_at`. Индекс `outbox_due` включает только ожидающие строки. Текст хранится
один раз, в прежнем зашифрованном поле истории. Метаданные доставки открыты и не
входят в AEAD: защита от изменения локальных статусов или отката базы не заявляется.

Переход v1 → v2 выполняется транзакционно после проверки владельца, ключа и старой
схемы; ошибка не оставляет частичную миграцию. Старые сообщения не меняются,
**старые исходящие не добавляются в очередь автоматически**. Версия 1 не содержала
достоверного статуса отправки, поэтому автоматическая отправка была бы опасной.
Обратной миграции нет; старый бинарник отклонит новую версию базы.

### API и завершение

`Service.Queue`, `Status`, `List` доступны для будущего интерфейса. `Changes` —
объединённое уведомление обновить данные, без передачи текста и без ожидания UI.
Сервис единолично потребляет `chat.Events`; другому слою нельзя читать тот же канал.
`Close` отменяет операции, закрывает сеть, ждёт обработчики/отправки и только затем
закрывает SQLite. Необработанные кадры могут остаться без ACK, ожидающие исходящие
остаются на диске. Сетевое соединение после отмены не считается доставкой.

## Гарантии и границы

Модель — повторяемая передача с дедупликацией локальной истории по стабильному ID.
Это не «ровно одна передача»: повторы нужны для восстановления. Общего сервера
нет, поэтому оба узла должны оказаться онлайн. На один профиль работает один
экземпляр сервиса/хранилища; несколько устройств, отзыв сообщений, read receipts,
порядок между разными собеседниками и автоматическое разрешение конфликтов ID
не реализованы. Обработчик приёма может задержать следующие события максимум
на срок записи ACK; затем применяется существующее ограничение очереди `chat`.

CLI/TUI пока используют прежние команды профиля и контактов. Новый API доставки
ещё не подключён к пользовательскому экрану чата. Обмен через публичный Tor
остаётся отдельно не подтверждённым; локальный транспорт в тестах его не заменяет.

## Проверки

Тесты охватывают потерю ACK, быстрый ACK до возврата Send, ACK другого контакта,
повторный ID, конфликт содержимого, ошибку сохранения без ACK, одновременные
enqueue/ACK/retry, ограничение работников, офлайн-собеседников, отмену отправки
и завершение без читающего UI. Проверяются миграция v1 без автоматической отправки
истории, восстановление очереди и срока попытки после выхода процесса без Close.
Сквозной тест использует сохранённые зашифрованные профили, настоящий взаимно
проверяемый TLS поверх локальных потоков, кадры `chat`, SQLite и перезапуск узла.
