# 0009. Кадры текстовых сообщений и подтверждений

Статус: принято.

## Контекст

`peers.Session` предоставляет защищённый поток байтов. Границы отдельных Write
не сохраняются транспортом, поэтому получателю нужен явный способ отделить
сообщения. До реализации чата и повторной доставки фиксируем формат, лимиты,
идентификаторы и поведение при повреждении потока.

## Решение

`internal/protocol` использует четыре байта длины в big-endian, затем JSON версии 1.
Тело ограничено 128 КиБ, текст — 16 КиБ в UTF-8. Длина проверяется до выделения
буфера тела. Максимальный текст помещается в кадр даже при экранировании каждого
байта шестью ASCII-символами JSON. Дополнительных библиотек нет.

Тип `text` содержит ID и текст. `ack` содержит только ID подтверждаемого сообщения.
Новые сообщения получают случайный ненулевой 128-битный ID через `crypto/rand`.
При повторной передаче сохраняется тот же ID. Проверять дубли и искать ожидающее
подтверждения сообщение нужно по паре «проверенный ключ собеседника + ID».
Полей отправителя, ника, адресата и времени в кадре нет: идентичность известна
из сессии, время приёма и порядок истории задаёт приложение.

ACK означает успешное постоянное сохранение сообщения получателем, а не чтение
человеком или простой приём байтов. Этот шаг реализует только кодирование ACK;
отправлять его после фиксации записи и обрабатывать в очереди будет `delivery`.
`protocol` никогда не создаёт подтверждение автоматически.

Версия 1 требует единственного представления JSON: фиксированные имена и порядок
полей, без пробелов вне строк, с правилами экранирования из [спецификации](../protocol.md).
После декодирования тело повторно кодируется и сравнивается побайтно. Это позволяет
отклонять неизвестные и повторные поля, различие регистра имён, `null` и тихую
замену повреждённого Unicode без отдельного самописного JSON-парсера.
Цена решения — сторонний клиент должен соблюдать эти правила сериализации.
Канонизация сама по себе не является шифрованием или проверкой подлинности.

Неизвестные версия и тип приводят к ошибке; согласование версий, необязательные
расширения, ping и сетевые пакеты ошибок пока не добавляются. ALPN защищённого
канала остаётся `shadowtalk/secure/1`: его подтверждающий байт читается до кадров.
Версия приложения проверяется в каждом кадре, независимо от версии TLS-канала.

## API и ответственность

- `Frame`, `TypeText`, `TypeAck`, `Frame.Validate` описывают данные приложения.
- `NewMessageID` и `ParseMessageID` создают и проверяют ID; wire-форма — 32 символа
  нижнего регистра hex. Нулевой ID зарезервирован для отсутствующего значения.
- `NewReader(io.Reader).ReadFrame()` читает ровно один кадр без чтения следующего.
- `NewWriter(io.Writer).WriteFrame(frame)` записывает полный кадр, включая
  повторные вызовы Write при частичной записи.

На поток создаётся один Reader и один Writer. Они могут работать одновременно;
несколько вызовов одного Reader или Writer сериализуются mutex. Это защищает
границы кадров при конкурентной записи, но не задаёт порядок сообщений диалога.

Модуль не владеет соединением и не запускает горутин. Контекст, дедлайны и закрытие
задаёт вызывающий код. Любая ошибка чтения и любая ошибка I/O при записи делают
соответствующий объект непригодным для продолжения: он сохраняет ошибку и больше
не выполняет I/O. Вызывающий код должен закрыть весь поток, включая второе направление.
Даже после timeout продолжать разбор нельзя: часть кадра могла уже пройти.
Ошибка проверки локального исходящего Frame возникает до I/O и разрешает исправление.

EOF допустим только перед новым заголовком. Неполный заголовок или тело возвращает
`io.ErrUnexpectedEOF`. Повреждённый кадр не пропускается в поисках следующего.
Успех WriteFrame не доказывает доставку; ошибка записи тоже не доказывает, что
получатель не получил сообщение. Очередь должна повторять исходный ID и устранять дубли.

Текст сохраняется без изменения, включая переводы строк и управляющие символы.
Безопасное отображение недоверенного текста — обязанность будущего TUI; печатать
полученный Text непосредственно в терминал нельзя. Ошибки разбора не содержат
исходного JSON или текста сообщения. Ограничение кадра не заменяет лимитов частоты
сообщений, очередей и истории на уровне приложения.

## Проверки и границы

Есть фиксированные wire-примеры, проверки частичных чтений/записей, последовательных
кадров, каждой точки обрыва, лимитов, Unicode, повреждённого JSON, версий, таймаутов
и конкурентной записи. Fuzz-тесты проверяют декодирование и чтение кадров.
Сквозной тест передаёт Unicode и текст максимального размера через сохранённые
профили, `peers`, два подставных Tor-процесса и TLS, затем явно передаёт ACK.
Он не проверяет постоянное сохранение или гарантии доставки.

Опциональный тест публичной сети тоже передаёт кадры, но его успешное прохождение
пока не подтверждено. Пользовательские команды отправки, диалоги, история,
автоматические ACK и очередь остаются следующими модулями.
