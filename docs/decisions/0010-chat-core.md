# 0010. Ядро живых диалогов

Статус: принято.

## Контекст

Сессии и формат сообщений готовы, но интерфейс не должен самостоятельно принимать
сокеты, читать кадры, разбирать встречные подключения или управлять горутинами.
Нужен модуль живого общения, к которому затем подключатся хранение, доставка и TUI.

## Решение

`internal/chat` работает с интерфейсом `Sessions`: `Connect`, `Accept`, `Close`.
Источник выдаёт только уже аутентифицированные соединения с подтверждённым контактом.
`chat.Session` содержит `net.Conn`, `Peer` и `Incoming`; ключи и Tor модулю не нужны.
После успешного `chat.Start` сервис владеет источником и всеми полученными потоками.
При неудачной проверке аргументов источник остаётся у вызывающего кода.

`app.PeerSessions.StartChat` связывает существующий запуск профиля, контактов и Tor
с этим интерфейсом через маленький адаптер. Параметры чата проверяются до чтения
профиля и запуска сети. Команд CLI и экранов чата этот шаг не добавляет.

`Service.Connect(ctx, alias)` возвращает существующий диалог или ждёт одну общую
попытку подключения для этого имени. Отмена одного ожидающего вызова не мешает
остальным; когда ожидающих больше нет, незавершённая попытка отменяется. Если
принятие соединения уже завершилось одновременно с отменой, диалог остаётся
собственностью сервиса. После успешного подключения контекст Connect его не закрывает.

Диалог идентифицируется проверенным публичным ключом, локальное имя служит поиску.
Входящие соединения принимаются автоматически из подтверждённого набора `peers`.
Изменения книги контактов по-прежнему требуют перезапуска сетевого ядра.

## Встречные соединения

Один диалог удерживает максимум один входящий и один исходящий поток. При встречном
подключении оба потока сохраняются: немедленное закрытие одного могло бы оборвать
уже передаваемый текст. Повторный поток того же направления закрывается.
Для записи используется первый принятый поток; чтение идёт с обоих. После отказа
основного можно использовать уже существующий второй поток в следующем Send.
Нового dial и повторной записи сообщения автоматически не происходит.

Вызовы Send внутри диалога сериализуются. Между потоками, при переключении потока
и между одновременно начатыми вызовами не обещается глобальный порядок сообщений.
Сохранение, устранение дублей, порядок истории и повторная доставка остаются
ответственностью следующих модулей. Один диалог не означает один физический поток.

## Сообщения и события

`chat.NewMessage(text)` создаёт ID, `Dialog.Send(ctx, message)` пишет один кадр.
Сообщение можно создать заранее и впоследствии сохранить до отправки. Успех Send
означает только успешную запись в соединение. Ошибка I/O может возникнуть уже после
приёма собеседником: исходный ID нужно сохранять для будущего механизма повторов.
Отмена до получения права записи не портит поток; отмена во время I/O закрывает его.

`Events()` — ограниченная очередь с одним потребителем. События содержат контакт
и сообщение либо полученный ACK. ACK остаётся заявлением проверенного собеседника;
сервис не сопоставляет его с outbox и не выставляет статус «доставлено».
Автоматических ACK нет, поскольку постоянного хранения ещё нет. Повторный ID
выдаётся как очередное событие, без скрытого удаления возможного дубля.

Если очередь заполнена, читатели останавливаются на публикации события. Память
не растёт без ограничения: кроме очереди, каждый читатель держит максимум один
разобранный кадр. Это обратное давление, а не постоянное хранение сообщений.
Текст остаётся недоверенным, в том числе содержащим управляющие символы; будущий
TUI обязан отображать его безопасно.

`Changes()` — отдельный сигнал перечитать `Dialogs()`. Несколько изменений могут
объединяться в один сигнал, это не журнал переходов. `Dialogs` возвращает текущие
handles, отсортированные по имени; сохранённый handle можно проверять через `Done`
и `Err` даже после удаления из списка. Завершение диалога не ждёт чтения событий UI.

## Лимиты и завершение

| Параметр | По умолчанию |
| --- | --- |
| `MaxDialogs` | 32 активных диалога и отдельно до 32 попыток подключения; максимум 1024 |
| `EventBuffer` | 128 событий; максимум 4096 |
| `ConnectTimeout` | 90 секунд на общую попытку подключения |
| `WriteTimeout` | 30 секунд, включая ожидание последовательной записи |
| `FrameTimeout` | 30 секунд после первого байта кадра до завершения его чтения |

Нули выбирают значения по умолчанию, отрицательные параметры недопустимы.
Лимиты `peers` действуют дополнительно; встречные потоки занимают два его слота.
Таймаут кадра не продлевается от поступления очередного байта. Молчание между
кадрами не ограничивается: открытый диалог без сообщений сохраняется.
Heartbeat и проверка присутствия собеседника в этой версии не реализованы.

Ошибка протокола закрывает весь нарушивший диалог. Ошибка I/O закрывает конкретный
поток; если других нет, завершается диалог. Отказ источника или отмена контекста
Start останавливает весь сервис. `Close` отменяет подключения, чтение, запись,
ожидание событий, закрывает источник и дожидается работников. Повторные Close
безопасны. После Done каналы закрыты; уже поставленные события можно дочитать.
Принудительное закрытие может отбросить кадр, который ещё читался или ожидал
места в очереди. Это не подтверждённое сообщение: ACK на него не отправлялся.

## Проверки

Покрыты двусторонний обмен, повторные и встречные подключения, параллельные Send,
отмена одного/последнего ожидающего Connect, лимиты, обрывы, медленный кадр,
переполнение очереди и завершение без читающего интерфейса. Проверяется сохранение
другого потока при обрыве одного и независимость соседних диалогов при плохом кадре.

Сквозной локальный тест создаёт зашифрованные профили с тестовым хранилищем ключей,
подтверждает приглашения и передаёт Unicode и максимальный текст через два
управляемых подставных Tor-процесса. Затем перезапускает один узел с тем же профилем.
Опциональный `TestTorSecureChannelLive` теперь использует ядро чата, но успешный
обмен через публичную сеть Tor пока не подтверждён.
