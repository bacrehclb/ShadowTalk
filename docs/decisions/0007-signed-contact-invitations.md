# 0007. Подписанные приглашения и локальные контакты

Статус: принято для локального знакомства v1.

## Контекст

Профиль имеет Ed25519-ключ и стабильный onion-адрес. Защищённый канал требует
точный ожидаемый ключ на обеих сторонах до рукопожатия. Ранний эскиз предлагал
одноразовый токен с секретом и подтверждением входящего запроса, но сетевой протокол
запроса и журнал расходования/отзыва ещё не были определены. Принимать неизвестные
ключи через готовый канал ради такого сценария нельзя.

## Решение

Первый законченный сценарий — взаимный обмен подписанными публичными приглашениями
и локальное подтверждение контактов. Токен содержит ник, v3 onion-адрес, публичный
ключ, случайный публичный ID, время выдачи и окончания действия. Он не содержит
seed или секрета доступа. Издатель подписывает payload ключом профиля через
`crypto.Signer`, с меткой назначения `ShadowTalk/invitation/v1\x00`.

Используется фиксированный JSON-формат в base64url без padding, версия 1,
лимит 2048 байт. Точный порядок полей и правила подписи описаны в
[протоколе](../protocol.md). Проверка канонического представления исключает
дубликаты и неоднозначные варианты кодирования. Подпись проверяется стандартной
библиотекой Go. Тестовый вектор дополнительно подготовлен Python `cryptography`.

Токен действует 24 часа по умолчанию, максимум 7 дней. Он многоразовый до срока;
новый токен не отзывает старый. Он не гарантирует доступность адреса в Tor.
Подпись доказывает целостность данных владельца ключа, а ожидаемый ключ человек
сверяет отдельно. Импорт требует точного полного SHA-256 отпечатка. Обе стороны
повторяют обмен, чтобы будущий TLS-сеанс мог использовать два сохранённых ключа.

`contacts.Book` хранит до 1000 записей: локальное имя, ник, onion, ключ и дату
подтверждения. Имена следуют правилам ника и учитывают регистр. Повторный импорт
тех же данных идемпотентен, а замена ключа/адреса занятого имени запрещена.
Собственная идентичность и дубли ключа/адреса под другим именем отклоняются.
Удаление требует полного отпечатка существующей записи. Для сознательной замены
нужно сверить новый ключ, явно удалить старую запись с её отпечатком и добавить новую.

Персистентность — `contacts.json` рядом с профилем. Формат версии 1 привязан
к публичному ключу владельца, ограничен 1 MiB, содержит только публичные записи.
Межпроцессная `.contacts.lock` сериализует чтение, изменение и публикацию.
Запись через временный файл того же каталога, sync, close и rename защищает
от обычной частичной записи. Power-loss durability и одинаковая атомарность rename
на всех файловых системах не заявляются. В Windows поведение проверит native CI.
Повреждение, неподдерживаемая версия и другой владелец не исправляются автоматически.
SQLite откладывается до сообщений/истории; интерфейс `app.ContactStore` позволяет
заменить адаптер без переноса правил доверия в SQL или UI.

CLI: `invite create/inspect`, `contacts add/list/show/remove`. Ввод токена — файл
или stdin, подтверждение — явный `--fingerprint`. Нет скрытого prompt в pipeline.
Справка работает без профиля и ключей. Список и изменения контактов используют
публичные метаданные профиля, выпуск токена требует приватного ключа в хранилище ОС.
Сетевых вызовов и изменений TUI в этом модуле нет.

## Последствия

- Можно подготовить и проверить контакты без доступной сети Tor.
- Двусторонний обмен требует больше действий; будущий запрос знакомства должен
  улучшить этот сценарий, сохранив явное подтверждение новых ключей.
- Одноразовые приглашения и отзыв потребуют версии протокола и состояния издателя;
  случайный ID сам по себе этих гарантий не даёт.
- Контакты переживают истечение токена. Удаление не отзывает переданный токен
  и не блокирует удалённую сторону на сетевом уровне.
- Публичность данных не означает отсутствие приватности: файл раскрывает связи,
  ники и адреса. Шифрование книги контактов остаётся отдельной задачей.
- Владение ключом на указанном onion-адресе проверяется TLS, а не локальным импортом.
  Реальный Tor-обмен остаётся отдельной проверкой (см. [Tor](../tor.md)).
