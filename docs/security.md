# Требования к защите данных

Ниже описаны реализованные механизмы и требования к следующим этапам.
Это не заявление о готовности всего мессенджера к защищённому общению.

`profile.json` версии 2 содержит ник, время создания и публичный Ed25519-ключ;
файл не зашифрован. Версия 1 с метаданными без ключей поддерживается для чтения
и явного `profile upgrade`. Новые каталоги и файлы создаются с режимами `0700`
и `0600` на Unix. Эти режимы не заменяют защиту ключей и настройку ACL на Windows.
`create` не заменяет существующий профиль. `upgrade` обновляет только старые
метаданные с теми же ником и датой. Повреждённая идентичность не заменяется новой.
В `identity` доступны генерация и восстановление Ed25519-ключей
из seed в памяти. Seed возвращается отдельной копией и позволяет восстановить
приватный ключ. CLI использует эти операции через `app.Profiles`; ключи шифрования
и seed в его вывод не попадают. Отпечаток — полный SHA-256 публичного ключа.

Шифрование seed в памяти использует AES-256-GCM из стандартной библиотеки Go
с автоматически создаваемым случайным nonce. Функции принимают отдельный
случайный ключ длиной 32 байта; это не пароль и не seed. Для привязки шифротекста
к назначению используется аутентифицируемая метка `ShadowTalk/identity-seed/v1`.
Неверный ключ или повреждённые данные не возвращают открытый seed.
Для отдельного ключа шифрования реализован адаптер `storage/keyring` на базе
`go-keyring`. Он хранит 32 байта в системном хранилище секретов; base64 служит
только текстовым представлением, защиту записи обеспечивает ОС. Отсутствие записи,
ошибка доступа и повреждённое значение различаются. Ошибки адаптера не содержат
ключ или исходный текст ошибки внешней библиотеки. Запасного хранения в обычном
файле нет. При ошибке проверки после `Set` запись уже могла произойти.
CLI использует адаптер для создания и загрузки профиля. На macOS/Windows/Linux
необходимо доступное системное хранилище; ОС может показать диалог разблокировки.

`Delete(id)` удаляет только указанную запись в пространстве ключей ShadowTalk.
Неверный ID отклоняется до доступа к хранилищу. Ошибка удаления или проверки
не раскрывает данные записи и не гарантирует, что ключ остался в хранилище.
Вызывающий код должен удалять только ключ, который больше не нужен для
расшифровки сохранённого seed. При ошибке `Set` сценарий удаляет только свой
новый ключ, до публикации seed. После ошибки публикации ключ сохраняется для `recover`.

`storage/seedfile` сохраняет только ID ключа и уже зашифрованный seed в отдельном
файле `identity-seed.json`. В нём нет открытого seed или ключа шифрования.
Адаптер проверяет размер и формат записи; целостность шифротекста проверяется
при вызове `identity.DecryptSeed` с ключом из хранилища ОС. Чтение повреждённого
файла не исправляет и не удаляет его. Запись не заменяет существующий файл.
Чтение файла, получение ключа и расшифровка объединены в `app.IdentityLoader`.
При отсутствии данных, отказе доступа или ошибке расшифровки он возвращает
пустую пару ключей и ошибку; новая идентичность автоматически не создаётся.
Полученный от хранилища буфер ключа и временный расшифрованный seed очищаются
после использования. Это не гарантирует удаления всех внутренних копий из памяти Go.
`Profiles.Load` также сравнивает восстановленный публичный ключ с `profile.json`.
Подмена шифротекста и ключа другой валидной парой при неизменных метаданных
отклоняется. Это не защита от полного контроля над учётной записью ОС.

Создание и обновление сериализуются блокировкой ОС. Журнал записывается до ключа
и содержит только публичные данные и шифротекст. `profile recover` продолжает
ту же идентичность; при отсутствии ключа отмена допустима только до публикации
файлов идентичности. Потеря ключа завершённого профиля не запускает регенерацию.
Восстановление после завершения процесса проверено; гарантии при отказе диска
или отключении питания не заявляются. Копии файлов без записи хранилища ОС
недостаточно для переноса или резервного восстановления.

`securechannel` использует TLS 1.3 стандартной библиотеки Go и обязательную
проверку точного Ed25519-ключа на обеих сторонах. Клиент отключает стандартную
проверку DNS/CA через `InsecureSkipVerify` только вместе с обязательной собственной
`VerifyConnection`; принимать произвольный сертификат через публичный API нельзя.
Проверяются подпись сертификата, срок, назначение, ограничения и ALPN. Владение
приватным ключом проверяет TLS. Сервер подтверждает завершение аутентификации
отдельным зашифрованным байтом; клиент ожидает его до выдачи готового канала.

Seed не нужен коду канала: он получает подписывающий объект через `KeyPair.Signer()`.
Сертификаты создаются заново для каждого соединения, не содержат ника и не сохраняются.
Общий лимит установки канала — 15 секунд по умолчанию, включая подтверждение сервера;
более ранний дедлайн контекста имеет приоритет. При ошибке исходный транспорт закрывается.
Ошибки возвращаются вызывающему коду без автоматического журналирования данных.
Первое доверие ключам, ограничения количества подключений, сообщения и защита
истории в этот модуль не входят. Формат и ограничения — в
[ADR 0005](decisions/0005-pinned-tls-channel.md).

`transport/tor` использует отдельный процесс и v3 onion-службу. Tor-ключ выводится
из seed профиля через HKDF-SHA256 с назначением `ShadowTalk/onion-service/v1`.
Он отделён от ключа подписи профиля; восстановление того же seed сохраняет адрес.
Это устойчивый идентификатор: адрес одного профиля связывает его сетевые сеансы.
Компрометация master seed раскрывает обе идентичности; отдельной ротации onion-ключа
в этой версии нет.

ControlPort и SOCKS слушают только `127.0.0.1` на случайных портах. Контроллер требует
SAFECOOKIE, проверяет путь cookie и ответ сервера; NULL-аутентификация отклоняется.
Cookie и временный torrc находятся в приватном каталоге запуска. Ключ ADD_ONION
передаётся только через этот аутентифицированный контроллер с `DiscardPK` и без
`Detach`. Адрес ответа сверяется с независимо вычисленным адресом. Seed и временные
буферы очищаются насколько позволяет Go; уничтожение всех копий в памяти не гарантируется.

SOCKS принимает только onion v3 с корректной контрольной суммой на фиксированном
виртуальном порту 443. Имена передаются Tor без локального DNS; `OnionTrafficOnly`
также ограничивает сам SOCKS-порт. Для каждого исходящего потока создаётся случайная
метка `IsolateSOCKSAuth`. Она служит изоляции цепочек, а не проверке контакта.
Успешный onion-connect обязательно дополняется взаимной проверкой ключей в TLS.

Потеря управляющего соединения завершает принадлежащий приложению Tor через
`TAKEOWNERSHIP`; до её установки действует `__OwningControllerProcess`.
Штатное закрытие и отмена ограничивают ожидание процесса, затем принудительно
завершают и дожидаются его. Отказ транспорта закрывает потоки без обхода Tor.
Raw control-ответы и stdout/stderr Tor не попадают в ошибки или журналы приложения.
Это уменьшает диагностику; пользователь получает этап сбоя и тип ошибки.
Каталог данных должен принадлежать пользователю; на Unix групповые/общие права
отклоняются. На Windows защиту каталога обеспечивает ACL учётной записи.

Локальная onion-служба пересылает подключения в loopback-listener. Процессы того же
пользователя могут обратиться к нему; контроль доступа обеспечивает следующий слой
TLS. Защита от захвата учётной записи ОС не заявляется. `peers` допускает только
сохранённые ключи, ограничивает все соединения (32 по умолчанию) и параллельные
входящие рукопожатия (8 по умолчанию), включая очередь ещё не принятых потоков.
TLS ограничен 15 секундами, исходящие dial и TLS вместе — 90 секундами.
Лимиты сдерживают параллелизм, но не предотвращают все формы отказа в обслуживании.

Книга контактов фиксируется при запуске менеджера. Удаление записи из файла
не отзывает доступ немедленно: нужно закрыть менеджер и запустить заново.
После перезапуска удалённый ключ больше не допускается. Автоматического принятия
неизвестных ключей, смены pin или прямого подключения в обход Tor нет.

- Приватные ключи остаются на устройстве и не входят в приглашения.
- Ключ собеседника проверяется при соединении. Изменение известного ключа
  требует отдельного подтверждения пользователя.
- Ник не доказывает личность человека. Для первого знакомства нужен способ
  сверки отпечатков ключей по доверенному каналу.
- Приглашения v1 имеют срок действия, но не обеспечивают отзыв или одноразовое принятие.
- Полные токены и содержимое переписки не попадают в диагностические журналы.
- Отказ Tor не приводит к автоматическому прямому соединению в обход Tor.
- Внешние данные проверяются по формату и размеру до обработки. Будущий интерфейс
  чата обязан отображать текст без выполнения управляющих последовательностей терминала.

Формат переносимой зашифрованной резервной копии ещё предстоит выбрать.
До пользовательского сетевого обмена — реализовать диалоги и доставку,
подключить сетевое ядро к интерфейсу и подтвердить обмен через публичную сеть.
Tor не защищает от доступа к разблокированному устройству или от разглашения
сообщений собеседником.

## Кадры сообщений

`protocol` проверяет четырёхбайтовую длину до выделения буфера: тело не больше
128 КиБ, текст после декодирования — не больше 16 КиБ UTF-8. Принимаются только
два типа версии 1 и ненулевой ID из 128 бит. Каноническая проверка отклоняет
неизвестные/повторные поля, повреждённый Unicode и альтернативные представления.
Ошибки разбора не включают содержимое сообщений.

После ошибки чтения или I/O записи, включая timeout, Reader/Writer не выполняет
новых операций. Приложение должно закрыть соединение целиком; модуль не ищет
следующий кадр в повреждённом потоке и не повторяет неоднозначно завершённую запись.
Лимиты размеров не заменяют ограничения частоты, очереди и объёма истории.
Дедлайны I/O задаёт приложение, а не кодек.

UTF-8 сам по себе не делает текст безопасным для терминала. Кодек сохраняет его
как есть, включая ESC и другие управляющие символы; экранирование и безопасный
вывод относятся к будущему TUI. Формат ACK не доказывает постоянное хранение сам
по себе: подтверждение должен отправлять слой доставки после фиксации записи,
а отправитель — проверять соответствие ID и аутентифицированного собеседника.

## Локальное подтверждение контактов

`contacts` проверяет Ed25519-подпись приглашения с отдельной меткой назначения,
строгий формат, размер, адрес и срок. Из токена не выполняются команды, DNS-запросы
или сетевые соединения. Недоверенные ник и адрес проходят ASCII-проверки до вывода
в терминал. Ошибки разбора и новые команды CLI не выводят исходный токен.
`invite create` выводит его только как явно запрошенный результат.

Добавление требует полного ожидаемого отпечатка ключа. Его нужно сверить
с собеседником по доверенному каналу: копирование из того же непроверенного токена
не защищает от подмены личности. Самоподписанный токен не доказывает контроль
onion-адреса; владение ожидаемым ключом на этом адресе подтверждается при TLS-соединении.
Поэтому сохранение контакта ещё не означает успешное соединение с собеседником.

Под занятым локальным именем другой ключ или адрес автоматически не сохраняется.
Повторное добавление той же записи сохраняет исходную дату. Один ключ или адрес
не может быть записан под несколькими именами. Удаление требует подтверждения
существующего отпечатка и действует локально. Сетевая блокировка, отзыв токена
и автоматическая ротация ключа в эту операцию не входят.

`contacts.json` содержит ключ владельца, локальные имена, ники, адреса, публичные
ключи и даты. Сами токены, seed и секреты в файл не записываются. Файл не зашифрован:
связи между людьми доступны тому, кто получил доступ к нему. Unix-права новых
файлов — `0600`; защита Windows зависит от ACL каталога профиля. Проверка ключа
владельца защищает от случайного смешивания профилей, не от изменения файла
процессом с правами пользователя. При повреждении или чужом владельце записи
не сбрасываются. Обнаружить удаление всего файла как потерю уже существовавшей
книги эта версия не может: отсутствие означает пустую книгу.
